# Pilot P-SG1 — APCCS Session-Guard Experiment

**Status:** Owner-approved at 14:03 America/Vancouver, 2026-11-05. Plan only; no guard values are adopted as code or a permanent rule.  
**Source:** Drive › Claude 2 › `SESSION_GUARD_RESEARCH_A6_2026-11-05` and `HANDOFF_ADDENDUM_6_PILOT_REPLAY_OPEN_STANDARDS_2026-11-05`.  
**Purpose:** Compare the current workflow with a guarded fresh-session workflow using the next batch work, then decide whether Arm B should be adopted, extended, or dropped.

## Protocol

- **Length:** The next 12 batch PRs across APCCS and UCLRCDE, alternating Arm A then Arm B in the order their PRs are opened (six batches per arm if all 12 complete), or two weeks, whichever comes first. Start after this plan is merged so the protocol is available to both build lanes.
- **Arm A:** Build as now, with no session guard.
- **Arm B:** Start a fresh session for each batch from shapes only: the batch's queue section, code map, and rules card. Put the rules at the top of every task message and a three-line reminder at the end. Hand off after the batch. Use a round cap of eight as a backstop.
- These are pilot settings, not code changes. Do not assign the session guard to A6. Decide whether and where it belongs only after the results.
- The builder records `Pilot arm: A` or `Pilot arm: B` in the PR description, outside the required eight-line record.

## Measures

Muse records one row per batch in the daily BUILD_HISTORY with:

1. Pilot arm.
2. Agent and model/version.
3. Rule breaks found in the audit.
4. Invented names or code-map mismatches.
5. Fix commits.
6. Red checks.
7. Owner taps or messages per batch.
8. Fresh-session resume: yes/no, based on whether the new session continues from the authorized shape without asking for information absent from it.
9. Estimated visible tokens at handoff, calculated as characters divided by four and labelled **estimate**. This does not estimate hidden-wrapper load.

## Decision rule and limits

At 12 batches or two weeks, whichever comes first, Muse records `PILOT_P-SG1_RESULT` in Claude 2. Adopt Arm B only if the combined count of rule breaks plus invented names falls by at least half and Owner taps do not rise. Otherwise extend the pilot or drop Arm B. Treat a small sample as evidence of only large differences, not proof of a universal best practice. Record missing measures instead of treating them as zero.

If Arm B creates a rule break, loses state, or increases avoidable Owner work, stop using it and return to Arm A while recording the result. Because this pilot changes only workflow settings, undo is to stop the B arm; no code rollback is needed. Keep the record and mark the result superseded rather than deleting it.

## Evidence boundary

The source research reports that none of the proposed numerical thresholds is verified for APCCS and that app-based hidden-wrapper load is not measurable by APCCS. P-SG1 tests a workflow; it does not claim to prove the source studies' results or establish a universal threshold.
