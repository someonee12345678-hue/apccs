# APCCS Master Director — local software first, replaceable AI workers

Date: 2026-11-06, America/Vancouver
Status: RESEARCH AND DESIGN PROPOSAL — not queued, installed, built or authorized for deployment.
Scope: Android phone-first; no local LLM required; no new paid service; no consumer-chat browser scraping.
Evidence: official project/vendor documentation retrieved for this report. VERIFIED means documentation supports the stated capability, not that it has been tested in the Owner's account.

## 1. The objective I take from the thread

One persistent project workspace, with one master chat as its front door. The Owner can speak, choose a toggle, inspect another worker's activity, and change who handles a job without reorganizing files or rebuilding context manually. The program files messages, decisions, tasks, code changes and evidence automatically. It uses ordinary software whenever that is sufficient, and does not spend model requests on bookkeeping.

The desired continuity belongs to APCCS, not to any particular company's chat window. The unit that moves between workers is a verified job and checkpoint. A provider's private internal state cannot be transplanted.

## 2. Recommended design

Build a small APCCS coordinator around the existing rules, log chain, gate and project files. Give it a phone-sized master chat, task cards and an activity drawer. Prefer an existing documented agent interface over building chatbot-site automation.

Use three execution paths:

1. **Software recipe:** validated structured input selects an already implemented, tested local operation. No model request.
2. **AI-assisted proposal:** a permitted agent proposes a shape, plan or patch. Deterministic checks and the existing authorization rules control what can happen next.
3. **Owner decision:** missing meaning or authority becomes a recorded question. Repeated approved decisions can inform future rules under A6; repetition alone never grants authority.

AI OFF must leave project browsing, filing, searching, task management, checkpoints, template generation, authorized deterministic recipes and evidence collection usable. It cannot provide unrestricted understanding of arbitrary English without a language model or a human.

The first specialist interface to investigate is **OpenCode** because it already documents a web interface, sessions and a local server API. The protocol to support is **ACP** where an agent implements it. Codex's own app-server is an alternative adapter with documented thread and progress methods. Keep every one of these replaceable; APCCS's record is not an opaque copy of the chosen tool's database. [S1–S6]

This is one architecture, not a requirement to install every tool listed below.

## 3. What the supplied thread gets wrong

| Claim or sample behavior | Correction and design consequence |
|---|---|
| A no-API GUI must automate chatbot websites. | False. Coding tools expose documented CLI, local protocol and server interfaces. These are APIs in the software sense, but need not require a separately billed developer key. Eligibility, quota and permitted authentication remain provider-specific. [S1–S7] |
| A desktop Tkinter window is the phone interface. | It does not establish an Android solution. Use a narrow web/native interface tested on the actual phone; avoid a desktop IDE layout. |
| The sample master GUI completes work. | Its success is generated by timers; the shown code does not execute the claimed worker, collect its response or persist verified task state. The first sample sends text and closes the browser without collecting a result. |
| Replacing four spaces compresses memory. | It is a text substitution that can alter code/string contents. It does not retrieve project state, resolve contradictions or establish a context budget. |
| A large master transcript guarantees continuity. | Keep original history, but derive a compact current-state view and retrieve relevant source material. Concurrent workers must not overwrite one shared Markdown file. |
| All processing is private because logs are local. | Cloud model input still leaves the device. Local ownership of records and local inference are separate properties. Case files remain excluded from off-device work. |
| AST construction makes code correct. | ASTs expose structure; they do not prove the generated program implements the intended behavior. Python even documents that parsing alone need not guarantee successful compilation. [S10] |
| Mypy, Ruff or mutation testing proves every execution path safe. | Type checking, linting and mutation testing have different scopes. A surviving mutation may be equivalent or outside relevant tests; it is not automatically a vulnerability. [S11] |
| Formal verification proves any application correct automatically. | Tools prove specified properties under their models and assumptions. Frama-C WP concerns C/ACSL contracts, not arbitrary APCCS Python. CrossHair expressly warns that no counterexample is not a guarantee. [S12–S13] |
| A code map can safely refactor everything. | It can identify dependencies and support a defined transformation. Dynamic references and intended behavior still require checking. APCCS's frozen/append-only rules prohibit blanket rewrites. |

No evidence in the thread establishes zero bugs, unlimited free inference, exact cross-company token counts or universal provider switching.

## 4. The phone experience

A single master screen shows:

- **Project:** APCCS or UCLRCDE, with separate files and permissions.
- **Master chat:** the Owner's messages and concise, evidence-linked status updates.
- **Work cards:** goal, assigned role/company, status, last evidence and blocker.
- **Activity drawer:** expandable worker messages, tool events, patches and tests.
- **Controls:** AI OFF / ASSIST / ON, preferred worker, Continue with another worker, Pause and STOP.
- **Connection card:** available, needs sign-in, quota reached, unsupported or not tested; last successful connection time.

The selected company is distinct from the role: architect, builder and checker are jobs, not fixed company identities. A checker must not audit its own build.

Example interaction:

> Owner: Add a progress report to this project.
>
> APCCS: I found the approved report recipe. It can use the saved project state without AI. Here is the planned output and destination.
>
> Owner: Use the recipe.
>
> APCCS: Report saved. Its source revision and receipt are attached.

If no recipe covers the request, APCCS prepares a proposal or an ASK field rather than pretending software inferred all the requirements. An instruction to build still follows the authoritative queue and permission process; casual chat does not silently mark new work ready.

Example switch:

> Owner: Continue this job with Gemini.
>
> APCCS: The old worker is stopped at checkpoint 4. The replacement received the approved inputs and unfinished step. The original attempt remains visible.

A request to view a worker opens its captured messages and events or a source link. It does not promise access to hidden reasoning or arbitrary existing consumer-chat threads.

## 5. Owned state and memory

Use **one project directory**, not one giant mutable conversation file.

| Record | Proposed storage and authority |
|---|---|
| Original Owner messages and imported source | Immutable UTF-8 artifacts with IDs and SHA-256; never silently rewritten |
| Event and decision receipts | Reuse the authoritative A2 log chain; attach canonical metadata and artifact references |
| Current tasks, search and relationships | Derived SQLite index, rebuildable from receipts and artifacts |
| Current project view | Human-readable Markdown/JSON projection, not a second source of truth |
| Code and proposed changes | Git base revision, isolated work branch and diff |
| Worker conversations | Separate runs linked to task ID; original records retained |
| Rules and approvals | Existing RULEBOOK, question ledger, queue and explicit approval evidence |
| Secrets | Remain in each provider's supported credential storage; never in messages, exports or project logs |

A single coordinator writes authoritative state. Worker processes submit events; they do not all append independently to a shared Markdown file. Update the derived index only after a durable receipt; after interruption, rebuild the index rather than invent missing completion.

A context packet includes goal, exact authoritative instructions, rules, source revision, relevant artifacts, completed steps with evidence, blockers and next action. Retrieve by project/task/source links and text search first. Vector embeddings and a graph database are not prerequisites.

Keep complete history outside the active model context. Preserve original code, comments and documents unchanged. A summary is a derived aid with source references, never the authority that erases earlier evidence. Provider-specific token measurements are stored when reported; other counts are labelled estimates. There is no invented universal token counter.

## 6. What ordinary software can build

The useful no-LLM component is a **catalog of tested recipes plus a constrained specification interpreter/compiler**.

A recipe has a version, input schema, allowed operations, output schema, normal and refusal examples, tests and undo procedure. It can compose existing approved components or generate bounded code from reviewed templates. Unsupported operations stop with ASK.

Candidate recipes:

| Work | No model needed once the recipe exists? | Boundary |
|---|---|---|
| File an artifact, hash it, deduplicate and record its source | Yes | Known path/data policy |
| Render a project dashboard from task state | Yes | Fixed views and fields |
| Create a report/export from approved records | Yes | Fixed template and source contract |
| Run syntax checks, approved tests and collect results | Yes | Approved isolated execution environment |
| Generate repeated validators/forms/report modules | Yes | Supported schema and reviewed templates only |
| Apply a predefined code transformation | Yes | Explicit transformation, preservation rules and tests |
| Invent a novel architecture from an ambiguous request | No general deterministic replacement established | AI or human specifies the new design |

Prefer interpreting simple workflow specifications over generating fresh Python for every job. A new approved report can then be data plus an existing renderer. Generate source only where a real artifact is needed.

A sample recipe specification might select a report type, approved input fields, destination and export format. It is not an arbitrary shell command or an executable expression. Never evaluate user text as code.

Existing tools demonstrate parts of this approach: Blockly generates code from blocks; MPS uses projectional models and generators; LibCST supplies explicit codemod machinery. They do not supply the complete APCCS product or infer arbitrary missing requirements. [S8–S9, S14]

## 7. Real connections instead of simulated success

- Can start a session?
- Can receive and return structured progress?
- Can resume its own saved session?
- Can cancel or checkpoint work?
- Can read/write only the allowed workspace?
- Which sign-in method, usage limits and cost policy apply?
- Has a round trip worked on this exact installation?

ACP standardizes client-agent communication, not universal cross-company memory or entitlement. Its registry is evidence of listed integration implementations, not proof that a specific authentication route is permitted or works on Android. The Muse Spark entry in that registry is not evidence about the Owner's Muse product. [S18]

The coordinator can connect to documented protocols while respecting a no-new-paid-API-key requirement. If “no API” literally means no programmatic interface at all, automated cross-company operation cannot be promised; the remaining route is user-driven native-app handoff.

Do not use unofficial login proxies, scraped cookies, fabricated completion events, shared accounts or automatic paid-credit fallback.

## 8. Switching safely while a job is running

The same APCCS task stays visible; each worker attempt gets its own run ID.

1. Stop or checkpoint the current worker. Freeze the approved source revision, completed-step receipts and current diff.
2. If cancellation cannot be confirmed, mark the worker's status unknown. Do not give another worker concurrent publishing rights.
3. Transfer a portable checkpoint with the goal, permitted paths, evidence and unfinished work.
4. Give the replacement a new attempt and a current ownership/fencing token. Its first response identifies the revision and next step.
5. Validate its output; accept a result only when its run and ownership version match the current task.
6. Archive the old attempt without deleting it.

Use at most one builder per repository/batch and one open PR per repository, retaining current project rules. Parallel researchers can work in separate read-only tasks; competing builders cannot share one mutable workspace.

Duplicate completion events must not open duplicate jobs. Lost events require reconciliation against durable run/PR state, not blind replay. If a worker has not sent evidence, show “status unknown” rather than “working” forever or “done” on a timer.

## 9. Local phone and server responsibilities

**Local first** means durable ownership and useful offline behavior. It does not mean the phone is guaranteed to execute indefinitely with its screen off.

A proposed phone implementation is a small web/native interface with a local coordinator. A Termux-hosted Python coordinator is an option because Termux is already part of the Owner's setup; its exact dependencies, storage permissions and restart behavior still require a device test. Termux documents a command/result bridge for a permitted Android app. Android background limits remain relevant. [S19–S20]

- Phone available: run approved lightweight recipes and show live events.
- Phone asleep/offline: preserve state; continue only jobs already accepted by a verified remote executor.
- Phone-only executor interrupted: queue waits and resumes; no always-on claim.
- Remote compute: GitHub Actions can perform already configured repository jobs; that does not establish a persistent general-purpose agent server.
- Reconnection: reconcile receipts and current revisions before dispatching anything else.

The standard-library APCCS core can use SQLite, JSON, hashing and existing tests. OpenCode, MPS, Blockly, Node-RED, LibCST and mutation frameworks are external software, not Python standard-library dependencies. Evaluating or using them needs its own authorized environment; this report does not add them to the repository.

Never run untrusted generated code beside private case files merely because both are local. A trusted recipe runner is different from a sandbox for arbitrary generated code.

| Candidate | Best fit | Recommendation |
|---|---|---|
| OpenCode | Ready-made multi-session coding interface and event-capable server | First reuse candidate to evaluate read-only; do not assume it supplies APCCS policy or supports every consumer subscription |
| ACP | Replaceable connection between compatible clients and coding agents | Support a verified compatible agent before adding more adapters |

| Blockly | Visual constrained programming/code generation | Design reference or later optional frontend; phone forms/cards may be easier than a large block canvas |
| JetBrains MPS | Language workbench and projectional code generation | Real relevant precedent, but its documented desktop requirements make it a poor first choice for this Android-only project [S21] |
| Node-RED | Visible event-driven flows and reusable subflows | Useful precedent/optional lab tool; adds Node.js/dependencies and is not the current stdlib APCCS core [S22] |
| LibCST / mutmut | Controlled refactoring and testing test quality | Optional isolated research tools, not a wholesale rewrite or proof of correctness |

The differentiating APCCS component should be its owned task state, enforceable authority, recipe catalog, evidence and recovery—not a new general-purpose IDE or another prompt-only generator.

## 11. Improvement without unsafe self-rewriting

Record what actually happened: recipe chosen, model requests, retries, errors, tests, elapsed time and Owner interventions.

- Cache only when inputs, recipe/tool versions, relevant rules and source revision match.
- Make repeated successful work a proposed recipe, not automatically trusted executable code.
- A6's three-repeat candidate still needs Owner approval before a rule is promoted.
- Try optimizations on an isolated replay set. Include bad inputs and interrupted-run cases.
- Keep the previous recipe version and compare results before adopting a new one.
- Never let the optimizer lower permissions, delete originals, change required checks or fabricate evidence.

“Learn” initially means improving an explicit, reviewable catalog and retrieval index. It does not require model training, and it does not promise autonomous invention of correct new software.

## 12. Smallest useful demonstration and acceptance gates

Do not begin by installing six agents or building swarms.

**Gate 1 — offline ownership:** In a throwaway project, create a task, file an artifact, run one software recipe, restart the coordinator and recover the task from durable records. AI OFF throughout. Show source and undo.

**Gate 2 — one genuine connection:** A read-only session reaches one permitted existing worker through a documented interface and returns a real structured result/progress event. The phone UI shows it. No keys are copied into chat.

**Gate 3 — controlled switch:** A second permitted worker resumes a checkpoint in the same visible APCCS job. Stop the first worker; reject late results and duplicate events. No unverified authentication fallback.

**Gate 4 — recipe value:** Run a small matched set of routine jobs using a recipe and the existing AI workflow. Measure model requests, correctness on held-out bad inputs, completion time, repair work and Owner interventions. Do not promise a percentage saving in advance.

**Gate 5 — builder integration:** Only after the above passes, propose a separately reviewed queue entry covering task leases, permitted execution, evidence and the phone UI. Preserve current branch/PR/STOP/merge rules. Do not assign this proposal A8 without an approved queue decision.

Failure paths: keep the master workspace and manual/native-app route if an adapter fails; keep the offline recipe path if no AI connection works; leave the queue waiting if execution or authority is unavailable. These are visible operating modes, not fake automatic success.
